DIGICHEESE — Projet de groupe (TP7)

Refonte d’un SI legacy (Access/VBA) : conception et livraison d’une API REST (FastAPI) + base MySQL, avec tests automatisés, documentation et pilotage projet (besoin → backlog → suivi).

Résumé

DIGICHEESE est un projet pédagogique mené en équipe dans le cadre du TP7. Le sujet simule la modernisation d’un système historique de gestion de cadeaux fidélité (Access + VBA) par une solution moderne : une API FastAPI documentée (Swagger), une base MySQL, des tests Pytest et une démarche projet outillée (expression de besoin, backlog produit, suivi).

Python FastAPI MySQL SQLModel / ORM Pytest Docker Compose Swagger / OpenAPI
Repo GitHub (backend) README / Quickstart
Note : l’IHM n’est pas le livrable principal du TP. Une UI Admin fonctionnelle (V1) a été proposée en complément pour démontrer l’utilisation des endpoints.

Contexte

Problème simulé et objectifs du TP.

Le SI historique (Access + VBA, ~20 ans) présente des limites : instabilité, maintenance difficile, ergonomie vieillissante. Le TP vise à concevoir une cible modernisée : une API exposant des endpoints REST, une base MySQL centralisée, et une démarche projet traçable.

Objectifs livrables

  • API FastAPI opérationnelle + documentation Swagger.
  • DB MySQL avec les tables nécessaires au CRUD Admin obligatoire.
  • Tests automatisés (Pytest) : au minimum 1 test nominal + 1 test erreur par ressource Admin.
  • Dépôt Git structuré + scripts SQL + documentation (fonctionnelle / technique / utilisation).
  • Backlog + board Agile + sprint fictif + retour d’expérience collaboration.

Périmètre

Ce qui est livré vs hors-scope.

IN (livré)

  • CRUD Admin sur les référentiels imposés par le TP (dont Objets et Conditionnements).
  • Documentation / Quickstart et conventions d’API.
  • Tests Pytest (nominal + erreurs) et traçabilité attendue.
  • Organisation projet (backlog, suivi, sprint fictif).

OUT (hors périmètre TP)

  • IHM complète (application web) — l’API est le livrable principal.
  • Fonctions avancées non demandées (reporting, monitoring, perf tuning, etc.).
  • Industrialisation au-delà du cadre TP.
Malgré le OUT, une IHM Admin (V1) a été proposée pour illustrer un usage réel des endpoints.

Vue d’ensemble technique (niveau portfolio).

L’architecture vise à rester simple, lisible et testable : endpoints REST (FastAPI) + modèles ORM, persistance MySQL, et tests automatisés. La documentation est exposée via Swagger (/docs).

IHM Admin (V1) — Front statique connecté à l’API

UI de démonstration : dashboard + CRUD Objets/Conditionnements + login (API key).

Pour rendre le projet plus “démontrable”, une UI Admin simple a été créée. Elle est statique (HTML/CSS/JS) et se connecte à l’API : dashboard de statut (/health), pages CRUD Objets et Conditionnements, et une page de login optionnelle.

Authentification

L’API attend un header X-API-Key. L’IHM stocke la clé (LocalStorage) et l’envoie à chaque requête. En environnement de dev, l’auth peut être désactivée via la variable DISABLE_AUTH=true.

Pages réalisées

  • Dashboard Admin : test du endpoint /health + raccourcis vers les référentiels.
  • CRUD Objets : GET / POST / PATCH / DELETE (filtre local V1).
  • CRUD Conditionnements : GET / POST / PATCH / DELETE.
  • Login : enregistrement d’une X-API-Key (optionnel selon config).
Notes : mapping des champs configurable dans js/config.js (si les noms de champs API diffèrent).
